Passo a passo

      
    

        
  1. 
          
    Modo ECB: encripta uma imagem
    
          
    
            
    A página desenha uma imagem de 64×64 pixels com três formas e encripta os bytes dos pixels de duas maneiras, com a mesma chave AES-256. No ECB cada bloco de 16 bytes é cifrado sozinho, por isso blocos iguais dão sempre cifrados iguais. No GCM cada bloco depende do contador e do IV, e o resultado parece ruído.

    O ECB não esconde as formas. Vê-se o contorno do que foi cifrado, apesar de nenhum byte ser legível. A criptografia não falhou: o AES continua inquebrado. Falhou o modo.
    
            
    Por dentroA Web Crypto nem oferece ECB, precisamente por ser perigoso. A página simula-o cifrando bloco a bloco com AES-CBC e IV zero, que no primeiro bloco é um AES puro. No terminal, openssl enc -aes-128-ecb faz o mesmo (ver terminal/).
    
            
    Como se evitaUsa sempre um modo autenticado com IV único: AES-GCM ou ChaCha20-Poly1305. Nunca ECB.
    
          
    
        
    2. 

        
  2. 
          
    IV repetido: recupera uma mensagem sem a chave
    
          
    
            
    O GCM funciona como uma cifra de fluxo: gera uma sequência de bytes a partir da chave e do IV (o keystream) e faz XOR com o texto. Se dois textos usam a mesma chave e o mesmo IV, o keystream é o mesmo, e ao fazer XOR dos dois cifrados o keystream desaparece:
    
            
    c1 = p1 XOR K
c2 = p2 XOR K
c1 XOR c2 = p1 XOR p2          // K cancelou
p2 = c1 XOR c2 XOR p1          // se conheces p1
    
            
    
              
    c1 XOR c2 (hex)
    (carrega no botão)
    
              
    p1 XOR p2 (hex)
    (carrega no botão)
    
              
    Resultado
    (carrega no botão)
    
            
    
            
    O atacante não usa a chave em momento nenhum. Recupera tantos bytes da mensagem secreta quantos tiver a mensagem que já conhece. Mesmo sem conhecer nenhuma, p1 XOR p2 revela muito sobre ambas, e texto em português tem muita estrutura.
    
            
    Pior aindaEm GCM, repetir o IV também compromete a autenticação: com dois pares de mensagem e etiqueta com o mesmo IV, um atacante pode, em teoria, recuperar a chave de autenticação e forjar mensagens. Este é o resultado conhecido do NIST SP 800-38D (secção sobre unicidade do IV). Aqui só mostramos a perda de confidencialidade.
    
            
    Como se evitaIV novo e aleatório de 12 bytes em cada encriptação (como a fase 1), ou um contador que nunca se repete. Se encriptares um número enorme de mensagens com a mesma chave, o IV aleatório de 96 bits acaba por colidir: roda a chave antes disso.

    Password fraca: adivinha-se
    
          
    
            
    A fase 1 deriva a chave AES da password. O AES-256 é inquebrável, mas a chave é tão forte quanto a password. A página encripta algo com a password sol2024 e depois tenta, uma a uma, as passwords de uma lista curta que escrevi. Cada tentativa deriva a chave e tenta decifrar: se a etiqueta GCM bater certo, acertou.

    As iterações do PBKDF2 não tornam uma password fraca forte. Só multiplicam o custo de cada tentativa. Uma lista real tem milhões de entradas, e quem ataca usa GPUs ou várias máquinas em paralelo, portanto os números desta página são um mínimo de referência, não uma previsão.
    
            
    Como se evitaPasswords longas e aleatórias (várias palavras ao acaso, ou de um gestor de passwords), e um número de iterações alto (a OWASP recomenda 600 000 para PBKDF2-HMAC-SHA256, confirma no cheat sheet atual). Para guardar passwords de utilizadores, melhor ainda é o Argon2id.

  4. 
          
    RSA pequeno: factoriza-se o módulo
    
          
    
            
    Uma chave pública RSA é um número n (o módulo) e um expoente e. O módulo é o produto de dois primos secretos p × q. A segurança do RSA assenta em factorizar n ser impraticável. Com um módulo pequeno não é: a página gera uma chave de 64 ou 80 bits, encripta uma mensagem, e depois, usando só n e e, factoriza n, calcula a privada d e decifra.

    Compara 64 e 80 bits: o tempo sobe muito mais depressa do que o tamanho. O algoritmo usado (Pollard rho) precisa de cerca de 2n/4 passos para um módulo de n bits, e o tempo varia de chave para chave porque os primos são aleatórios; nas minhas corridas, 80 bits demorou dezenas de vezes mais do que 64. Um módulo de 3072 bits está muito, muito para lá do que isto consegue. Mesmo os melhores algoritmos conhecidos (crivo geral do corpo de números) não chegam lá: o NIST estima cerca de 128 bits de segurança para RSA-3072.
    
            
    AtençãoIsto é RSA "de manual", sem padding, só para a demonstração. O RSA a sério usa OAEP (fase 2). Os 64 e 80 bits aqui são brinquedos; hoje o mínimo aceitável é 2048 bits, e 3072 é a recomendação para uso a longo prazo.
    
            
    Como se evitaRSA de pelo menos 2048 bits (melhor 3072) ou curvas elípticas (P-256, Curve25519). Gera as chaves com uma biblioteca, nunca à mão.

  5. 
          
    O que aprendeste
    
          
    
            
      
              
    1. Um algoritmo forte não salva um modo errado (ECB).
      2. 
              
    2. Os parâmetros que "são só números" (IV) são requisitos de segurança.
      3. 
              
    3. A chave derivada de uma password nunca é mais forte do que a password.
      4. 
              
    4. Tamanhos de chave têm um mínimo, e abaixo dele a conta é feita em milissegundos.
      5. 
            
    
            
    Todos estes erros são evitáveis com bibliotecas bem escolhidas e as configurações por defeito. Quando não as usas, és tu a escolher o modo, o IV, o tamanho e o padding, e é aí que as coisas correm mal.

Em resumo

      
ECB mostra padrões, IV repetido deixa recuperar texto sem chave, passwords fracas adivinham-se e módulos RSA pequenos factorizam-se. Em todos os casos a matemática do AES e do RSA continua certa; o que falhou foi o uso.
